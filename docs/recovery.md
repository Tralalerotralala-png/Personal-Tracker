# Data recovery and backup scope

- Cloud records live in Supabase; account-bound IndexedDB caches are not encrypted. A previously authorized account can use its cached records while offline and upload when reconnected.
- Photo selections and removals now commit the item's photo path, local image bytes, retry marker and structured-record outbox **together in one IndexedDB transaction**. If device storage rejects the write, the previous photo remains intact. The Sync pill explicitly reports photo uploads still waiting independently of record synchronization, and supports a manual retry. Do not clear browser storage while image uploads remain pending.
- If a photo is replaced while an earlier photo is still uploading, each cloud photo has its own object path and the pending upload marker remains attached to the newest selected image. An older in-flight upload cannot acknowledge or erase a newer photo's retry marker. Likewise, a delayed signed-image download will not overwrite the current item's newer cached photo, even if it returns after a replacement was selected.
- Cloud photos removed or replaced in the app are **not immediately deleted from Supabase Storage**. The old file is retained for a **seven-day recovery period**, then deleted only when this device is online, the relevant item has no pending changes, and a fresh authorized server query confirms **no owner item** still references that path. Failed checks leave a retry marker in device storage. This avoids deleting an image that another device or an unsynced server record still needs; temporary extra Storage usage is expected, and clearing this device's browser storage also clears deferred-cleanup markers.
- A device that has successfully loaded cloud configuration remembers this mode. If `config.js` is later missing, invalid or temporarily unavailable, startup stops with a recovery message **rather than silently opening a separate local sample-data database**. Restore the published `config.js` and reload; do not clear browser site data while troubleshooting unsynced records.
- Ordinary sign-out preserves pending offline edits. For shared computers, **Settings > General > Erase account data from device** is a separate destructive action blocked while structured records or photos await upload. It offers an export of local conflict copies, then clears account record tables, cloud outbox, all account-bound metadata (including private photo bytes), the separate imported-audio IndexedDB database and account audio preferences. It signs out locally after device erasure. Cloud data is not deleted. Close other Tracker tabs first; otherwise they can recreate cached records on the same device.
- Before changing a legacy unverified browser cache, export it from Settings > General. The old cache has no reliable owner stamp. Review the file; never attach it automatically to an account.
- The **original JSON structured backup** contains all seven record tables, including soft deletion markers and personal settings. It intentionally does **not** include image binaries, remote game backup files or imported audio. It remains supported for small, fast structured restores.
- Uploading a private game save now also requires Supabase to acknowledge the owner-scoped, per-backup metadata row before the app reports the backup as fully saved. If the local browser database fails, the app attempts a direct cloud-index write; if cloud confirmation fails, the uploaded Storage bytes are retained instead of being automatically deleted. Keep the original save until the index is confirmed, and do not clear the browser cache while a cloud index is pending.
- Deleting a private game-save file now requires the owner-scoped pending-deletion marker to be **confirmed by Supabase** before removing the Storage object, and confirms the final deletion tombstone afterward. If the network fails, the file remains intact until the first confirmation succeeds. A second device can display and retry an unfinished deletion rather than showing a mysteriously missing file. This is a recoverable two-step workflow, **not** an atomic transaction across SQL and Storage; keep an independent copy of irreplaceable saves.
- **Portable TAR backup (Settings > Data & tools)** combines the same structured records with photos, private game-save files, and device-local audio. You can select Everything, or export smaller categories. Photos and game saves require access to their Supabase Storage objects unless already cached. Missing/unavailable files stop a full export instead of being silently omitted. If local-only settings still reference private cloud game saves, selecting those saves in an export now produces an explicit error until you can export them from the owning cloud account. A partial archive explicitly records which categories it covers.
- A TAR file is a standard archive (`tar -tf file.tar`, `tar -xf file.tar` on desktop). Its `manifest.json` includes record metadata, file paths, a SHA-256 checksum of the structured JSON records, and per-1 MiB SHA-256 checksums for media (older version-1 TARs without the structured-record checksum remain readable). Each media file is verified **before** import starts. It is *not encrypted* and may contain private readable records, photos, music and save files. Protect it accordingly.
- Current safety bounds are **150 MB per media file**, **512 MB per TAR** and **50 MB per JSON manifest**; export smaller groups if you exceed the limit. The feature uses Blob-backed file parts, and temporary browser resources may still be required. Avoid running large exports in a low-memory tab.
- The portable restore is merge-only and requires the **same Supabase account ID or the same local-only storage mode** as the export. Cross-account media paths are deliberately rejected, not silently re-owned. You should retain the original TAR for retries. It preflights every media checksum and record, downloads a structured-record checkpoint, then uploads missing private cloud media, atomically merges the local structured records, and restores local media caches. For local-only photos, the app preserves a newer, matching cached photo when merging an older TAR even if both photos share the same `local/<item-id>` path. A device-storage failure after record import may leave a **partial media restore**; it is reported for retry, not concealed. The original archive remains unaffected.
- Restore performs complete preflight validation and one atomic local database transaction, but cannot roll back writes already accepted by a remote server. Restore only while your account is stable and the sync queue is healthy.
- The app downloads a safety checkpoint of current structured records before a manual merge restore. Protect that JSON as a sensitive document; it may include private settings and encrypted journal ciphertext.
- **New Logs format (v3):** Every dream, sleep record, mood, habit, private-vault entry and encrypted draft now lives in a separate owner-scoped `settings` record with a randomly generated AES-GCM nonce. An authenticated 600,000-iteration PBKDF2-derived key encrypts each record; only a shared encrypted key verifier and salt are stored alongside them. Titles, dates, bodies and images never sync as plaintext. Unrelated entries edited offline on different devices now merge independently rather than overwriting one large journal blob.
- **Where previous Logs are archived:** They remain in their **original** synced `settings` row with key `private_journal_v1` (or the same account-scoped local IndexedDB record in local-only mode). This is **not** a separate file or folder; a structured JSON backup contains the encrypted value, which still needs the original PIN/passphrase to decrypt. The new app only reads `private_journal_v3_header`, `private_journal_v3_entry:*`, and `private_journal_v3_draft:*` for active Logs. No old records were automatically deleted or transferred into v3.
- **Passphrases and old Logs:** New Logs require a 12–128-character passphrase. If the device has an older `private_journal_v1` record, the v3 journal starts fresh; **the old encrypted v1 record is left untouched, but it is not shown in the current Logs screen**. Download a full structured backup before removing site data if you want to preserve that historical ciphertext. Do not discard the legacy PIN if you may want to recover the archived record with older software. Lost v3 passphrases cannot be recovered.
- **Changing the Logs passphrase:** The new key verifier, every encrypted entry and every encrypted draft are rotated in one local IndexedDB transaction, never partially. Other devices must re-unlock with the new passphrase after syncing. **Finish syncing and close Logs on all other devices first**: an offline device can otherwise re-upload an entry encrypted with an obsolete key. This is surfaced as a readable error, not silently deleted.
- **Resolving an edit conflict:** Edits to the same entry can still conflict. Supabase's last-write-wins synchronization preserves losing ciphertext in the original device's local conflict recovery cache. While Logs is unlocked, choose **Review conflicting entries** to inspect readable copies and **Restore as a new entry** so the winning version remains intact. Recovery snapshots from an older passphrase may be unreadable; export them from the Sync status dialog before clearing that device.

A cloud write rejected by last-write-wins, or a newer remote row arriving during a pending local edit, can produce an account-scoped, device-only conflict copy in IndexedDB meta. The downloaded row and its recovery copy commit in one local database transaction. Export these from Settings > General > Export conflicting edits. This is a safety net, not a full multi-device conflict resolver; compare versions manually. If the browser data is deleted, these copies disappear too.

- Sync conflicts are visible in the Sync status dialog and can be exported as device-only snapshots. Different Logs entries now sync independently, but conflicting edits to **the same entry** are still last-write-wins. Conflict copies are not a server backup; preserve the device cache until they have been reviewed.
