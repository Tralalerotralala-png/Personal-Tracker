# Data recovery and backup scope

- Cloud records live in Supabase; account-bound IndexedDB caches are not encrypted. A previously authorized account can use its cached records while offline and upload when reconnected.
- A device that has successfully loaded cloud configuration remembers this mode. If `config.js` is later missing, invalid or temporarily unavailable, startup stops with a recovery message **rather than silently opening a separate local sample-data database**. Restore the published `config.js` and reload; do not clear browser site data while troubleshooting unsynced records.
- Sign-out preserves pending offline edits. For shared computers, **Settings > General > Erase account cache from device** is a separate destructive action blocked when uploads remain.
- Before changing a legacy unverified browser cache, export it from Settings > General. The old cache has no reliable owner stamp. Review the file; never attach it automatically to an account.
- The **original JSON structured backup** contains all seven record tables, including soft deletion markers and personal settings. It intentionally does **not** include image binaries, remote game backup files or imported audio. It remains supported for small, fast structured restores.
- **Portable TAR backup (Settings > Data & tools)** combines the same structured records with photos, private game-save files, and device-local audio. You can select Everything, or export smaller categories. Photos and game saves require access to their Supabase Storage objects unless already cached. Missing/unavailable files stop a full export instead of being silently omitted. If local-only settings still reference private cloud game saves, selecting those saves in an export now produces an explicit error until you can export them from the owning cloud account. A partial archive explicitly records which categories it covers.
- A TAR file is a standard archive (`tar -tf file.tar`, `tar -xf file.tar` on desktop). Its `manifest.json` includes record metadata, file paths, a SHA-256 checksum of the structured JSON records, and per-1 MiB SHA-256 checksums for media (older version-1 TARs without the structured-record checksum remain readable). Each media file is verified **before** import starts. It is *not encrypted* and may contain private readable records, photos, music and save files. Protect it accordingly.
- Current safety bounds are **150 MB per media file**, **512 MB per TAR** and **50 MB per JSON manifest**; export smaller groups if you exceed the limit. The feature uses Blob-backed file parts, and temporary browser resources may still be required. Avoid running large exports in a low-memory tab.
- The portable restore is merge-only and requires the **same Supabase account ID or the same local-only storage mode** as the export. Cross-account media paths are deliberately rejected, not silently re-owned. You should retain the original TAR for retries. It preflights every media checksum and record, downloads a structured-record checkpoint, then uploads missing private cloud media, atomically merges the local structured records, and restores local media caches. For local-only photos, the app preserves a newer, matching cached photo when merging an older TAR even if both photos share the same `local/<item-id>` path. A device-storage failure after record import may leave a **partial media restore**; it is reported for retry, not concealed. The original archive remains unaffected.
- Restore performs complete preflight validation and one atomic local database transaction, but cannot roll back writes already accepted by a remote server. Restore only while your account is stable and the sync queue is healthy.
- The app downloads a safety checkpoint of current structured records before a manual merge restore. Protect that JSON as a sensitive document; it may include private settings and encrypted journal ciphertext.
- **New private journals and key changes now require a passphrase of 12–128 characters.** Four-digit PINs created by older versions can still unlock existing encrypted entries, but they offer weak protection against offline password guessing. If you still use a legacy PIN, unlock the journal and choose **Change PIN / key** to rotate to a long unique passphrase. A lost key cannot be recovered.

A cloud write rejected by last-write-wins, or a newer remote row arriving during a pending local edit, can produce an account-scoped, device-only conflict copy in IndexedDB meta. The downloaded row and its recovery copy commit in one local database transaction. Export these from Settings > General > Export conflicting edits. This is a safety net, not a full multi-device conflict resolver; compare versions manually. If the browser data is deleted, these copies disappear too.
